# M-Trace 설계 논의 요약

작성 기준: 2026-10-22

이 문서는 M-Trace 기획 대화에서 합의하거나 검토한 주요 설계 방향을 다른 개발 환경에서도 이어볼 수 있도록 정리한 요약입니다. 원문 채팅 전체를 그대로 옮긴 기록은 아닙니다.

## 솔루션 개요

**M-Trace**는 WEB·WAS·APM 운영 데이터를 연결해 서비스 요청 흐름과 장애 원인을 추적하는 솔루션입니다. 특정 미들웨어 제품 자체의 장애를 진단하는 도구라기보다, 여러 계층의 관측 정보를 요청 단위로 연결하고 운영자가 확인할 근거와 절차를 제시하는 것을 목표로 합니다.

핵심 메시지:

1. 이기종 운영 로그를 공통 형식으로 정규화
2. WEB·WAS 요청 흐름을 한 화면에서 가시화
3. Trace ID를 핵심 연결 키로 사용하고 시간·요청 URL·인스턴스 정보를 보조 근거로 결합해 분석 신뢰도를 높임

## 요청 상관분석 방향

- WEB, WAS, 지원 가능한 APM에 공통 Trace ID가 기록되도록 구성하고, 동일 ID를 기준으로 관련 로그와 트랜잭션을 요청 단위로 연결합니다.
- 두 가지 ID 전파 대안을 검토했습니다.
  - WEB에서 ID를 발급하고 요청 헤더로 WAS에 전달한 뒤 WEB·WAS 로그에 기록
  - WAS에서 ID를 발급하고 응답 헤더로 WEB에 전달한 뒤 WEB·WAS 로그에 기록
- 실제 발급 위치, 헤더 이름, 프록시 전달, 로그 포맷 및 APM 설정은 고객 환경에 맞게 검증·구성해야 합니다.
- 요청 URL, 호스트, 서비스·인스턴스 관계와 시간은 흐름을 설명하는 보조 정보로 활용합니다. 시간상 가까운 신호만으로 같은 요청이나 인과관계를 단정하지 않습니다.
- JMX 등 요청별 Trace ID가 없는 집계 지표는 인스턴스와 시간 구간을 기준으로 주변 맥락으로 제시하고, Trace ID에 직접 연결된 증거와 구분합니다.
- 데이터가 누락되거나 ID가 일치하지 않는 경우 연결 실패·근거 부족을 표시하고, 원인 확정 대신 근거가 있는 후보와 운영자 확인 절차를 제공합니다.

## Agent 및 수집 아키텍처 방향

- 제품 사용자는 운영 서버에 설치하는 구성요소를 **M-Trace Agent** 하나로 인식하도록 합니다.
- Fluent Bit은 로그 파일 수집·전달을 위해 내부에서 포함·실행·관리하는 구현 후보입니다. Fluent Bit 자체에는 기본 JMX MBean 입력이 없으므로 JMX 수집은 별도 기능 또는 커넥터로 구현해야 합니다.
- Fluent Bit을 포함해 패키징하더라도 OS 프로세스 관점에서는 별도 Fluent Bit 프로세스일 수 있습니다. 단일 제품 설치와 단일 OS 프로세스는 구분합니다.
- 고객 서버에서 M-Trace 서버로의 통신은 아웃바운드 TCP/TLS를 우선 검토하고, 인증·방화벽·버퍼·재시도·자원 제한·읽기 전용 권한을 설계해야 합니다.
- Scouter는 선택 가능한 APM 연계 대상입니다. 이미 다른 APM이 있는 고객에게 별도 APM Agent 설치를 기본 요구하지 않고, 해당 APM의 헤더 기반 추적 및 데이터 조회·연계 방법을 확인합니다.
- 고객 환경별 Agent 부하, 로그 경로·권한, JMX 접근, 개인정보 마스킹, 데이터 보존·삭제 정책을 검증해야 합니다.

## 분석 방법 및 화면 방향

1. 로그·트랜잭션 데이터를 공통 이벤트 형식으로 정규화합니다. 후보 필드에는 시각, Trace ID, 서비스·인스턴스, 이벤트 유형, 요청 경로, 상태, 처리 시간, 원본 위치가 포함됩니다.
2. Trace ID로 WEB·WAS·APM에 기록된 같은 요청을 매칭합니다.
3. 매칭된 요청의 로그와 구간 정보를 시간순으로 재구성하고 원본 근거를 제공합니다.
4. Trace ID가 없는 지표는 해당 인스턴스와 요청 처리 시간대의 맥락으로 표시합니다.
5. 분석 결과에는 사용한 증거, 데이터 누락·불일치, 후보의 한계를 함께 보여줍니다. 상관관계는 근본 원인의 증명이 아닙니다.

화면 방향:

- 등록된 WEB/WAS/APM 인스턴스 및 연결 관계
- Trace ID 기준 요청 목록과 상세 타임라인
- 연결된 WEB·WAS 로그 및 선택 APM 트랜잭션
- 같은 인스턴스·시간 구간의 보조 지표
- 각 연결 근거의 출처와 누락·불일치 표시

## 초기 DB 설계 후보

화면과 분석을 구체화할 때 다음 엔터티를 기준으로 ERD와 PostgreSQL DDL을 설계합니다.

- `environment`: 고객·운영 환경
- `service_instance`: WEB/WAS/APM 인스턴스와 호스트
- `instance_relation`: WEB→WAS 등 인스턴스 관계
- `trace`: `(environment_id, trace_id)` 범위의 요청 요약
- `trace_event`: 같은 요청의 WEB/WAS/APM 구간
- `log_event`: 정규화 로그 이벤트와 원본 위치
- `metric_sample`: Trace ID가 없는 JMX/APM 지표
- `trace_evidence`: 요청에 연결된 로그·지표, 연결 방식과 근거 수준

원문 로그를 저장할지 참조만 할지, 보존 기간, 파티셔닝·인덱스, URL·로그 민감정보 마스킹을 설계 단계에서 정해야 합니다.

## 예상 챌린지

1. 트랜잭션 수집 범위, 데이터량, 보존 기간 및 저장·검색 비용
2. 기존 APM의 추적 기능과 비교한 M-Trace의 차별점과 추가 가치
3. Trace ID 전파 실패·누락·재발급 시의 연결 처리
4. 고객별 제품·버전·로그 형식 차이에 대한 지원 범위
5. Agent의 CPU·메모리·디스크·네트워크 사용량과 운영 영향
6. 민감정보, 전송 암호화, 접근 권한, 폐쇄망, 보존·삭제 정책
7. Trace ID 상관관계와 근본 원인 증명의 구분 및 근거 한계
8. 초동 대응 시간·조사 노력 절감과 고객의 지불 의사 검증
9. 기존 도구가 해결하지 못하는 구체 업무와 우선 해결할 문제
